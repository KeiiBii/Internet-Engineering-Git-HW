### سؤال ۱: merge و rebase

* **عملکرد `git merge`:** تغییرات یک شاخه را با شاخه جاری ترکیب می‌کند بدون اینکه تاریخچه کامیت‌های قبلی بازنویسی شود. معمولاً یک "کامیت ادغام" (Merge Commit) با دو والد ایجاد می‌کند که نشان‌دهنده ترکیب دو مسیر توسعه در تاریخچه است.
  * **موقعیت استفاده:** برای ادغام یک قابلیت تکمیل‌شده (Feature) در شاخه اصلی (مثلاً `main`).
  * **دلیل:** چون شناسه کامیت‌ها را حفظ می‌کند و رابطه شاخه‌ها در تاریخچه دست‌نخورده باقی می‌ماند (مناسب برای کار گروهی و شاخه‌های مشترک).

* **عملکرد `git rebase`:** کامیت‌های شاخه جاری را برمی‌دارد و آن‌ها را روی آخرین وضعیت یک شاخه دیگر (مثلاً `main`) دوباره اعمال می‌کند. این کار تاریخچه را بازنویسی کرده و یک تاریخچه خطی و تمیز (بدون کامیت ادغام) می‌سازد.
  * **موقعیت استفاده:** به‌روزرسانی شاخه محلی (Local) خودتان با آخرین تغییرات `main` قبل از اینکه آن را پوش (Push) کنید.
  * **دلیل:** تاریخچه را خطی و خواناتر می‌کند. اما هرگز نباید روی شاخه‌هایی که قبلاً با دیگران به اشتراک گذاشته‌اید استفاده شود، زیرا با بازنویسی تاریخچه، کار هم‌تیمی‌ها مختل می‌شود.

### سؤال ۲: انتخاب بخشی از تغییرات

* **مفهوم hunk:** منظور از بخش (hunk)، مجموعه‌ای از تغییرات نزدیک به هم در یک فایل است که گیت در خروجی `diff` به همراه چند خط زمینه (برای نشان دادن محل تغییر) نمایش می‌دهد.
* **روش تعاملی:** با استفاده از دستور `git add -p <file_name>` وارد حالت تعاملی می‌شوید. گیت هر hunk را جداگانه نشان داده و از شما می‌پرسد چکار کند.
  * **گزینه y:** بخش را به ناحیه Staging اضافه می‌کند.
  * **گزینه n:** بخش را نادیده می‌گیرد (در Working Tree می‌ماند).
  * **گزینه s:** در صورت امکان، بخش را به قطعات کوچک‌تر تقسیم می‌کند.
* **فایده:** این کار کمک می‌کند تا تغییرات نامرتبط (مثلاً رفع باگ و تغییر فرمت یک فایل) را از هم جدا کنید و کامیت‌های منطقی، منسجم و تک‌هدفه بسازید که بازبینی آن‌ها آسان‌تر است.

### سؤال ۳: یافتن منشأ خطا

* **عملکرد `git bisect`:** از جستجوی دودویی (Binary Search) در تاریخچه برای یافتن اولین کامیتی که باعث ایجاد خطا شده است استفاده می‌کند.
* **مراحل جستجو:**
  1. شروع: `git bisect start`
  2. تعیین نسخه خراب فعلی: `git bisect bad`
  3. تعیین یک نسخه سالم قدیمی: `git bisect good <commit_hash>`
  4. گیت یک کامیت میانی را برای شما چک‌اوت می‌کند. شما تست می‌کنید: اگر سالم بود می‌زنید `git bisect good` و اگر خراب بود `git bisect bad`.
  5. این کار تکرار می‌شود تا گیت اولین کامیت معیوب را معرفی کند.
  6. خروج و بازگشت: `git bisect reset`
* **مثال و فایده:** فرض کنید بین ۶۴ کامیت یک باگ ورود کاربر پیدا شده است. به جای تست تک‌تک آن‌ها، با bisect نهایتاً با ۶ بار تست به منشا باگ می‌رسید که بسیار در زمان صرفه‌جویی می‌کند.

### سؤال ۴: بررسی تغییرات پیش از کامیت

1. دستور `git diff` تغییراتی که هنوز وارد Staging نشده‌اند (وضعیت Working Directory نسبت به Staging) را نشان می‌دهد. دستور `git diff --cached` (یا `--staged`) تغییراتی که آماده کامیت هستند (وضعیت Staging نسبت به آخرین کامیت) را نشان می‌دهد.
2. اگر از دستور `git commit -m "msg"` استفاده کنید، فقط تغییراتی که در ناحیه Staging قرار دارند ثبت می‌شوند. تغییرات ثانویه‌ای که در فایل انجام داده‌اید اما Add نکرده‌اید و همچنین فایل‌های پوشه `tmp` در Working Tree باقی می‌مانند. دلیل آن این است که گیت فقط محتوای فعلی ناحیه Staging را برای ساخت کامیت در نظر می‌گیرد.
3. باید فایل `.gitignore` را در ریشه پروژه ایجاد یا ویرایش کنید و نام پوشه `/tmp/` را در آن بنویسید. اگر فایلی قبلاً Track شده باشد، اضافه کردن آن به `.gitignore` کافی نیست؛ گیت همچنان آن را دنبال می‌کند. باید ابتدا با دستور `git rm --cached <file>` آن را از حالت پیگیری (Tracking) خارج کنید.

### سؤال ۵: رفع merge conflict

1. Conflict به این دلیل رخ داده که هر دو نفر دقیقاً یک خط مشابه از یک فایل واحد را به دو شکل متفاوت تغییر داده‌اند. خیر، هر تغییری باعث Conflict نمی‌شود؛ اگر تغییرات در فایل‌های متفاوت یا حتی در خطوط کاملاً مجزای یک فایل باشند، گیت معمولاً آن‌ها را به صورت خودکار ادغام (Auto-merge) می‌کند.
2. با دستور `git status` فایل‌های دارای اختلال (Unmerged paths) مشخص می‌شوند. در فایل، مارکرهای `<<<<<<< HEAD` (تغییرات شما)، `=======` (خط جداکننده) و `>>>>>>> branch_name` (تغییرات هم‌تیمی) اضافه شده‌اند که مرز دقیق اختلافات را نشان می‌دهند.
3. **مراحل رفع:**
   * فایل را در ادیتور باز می‌کنیم و هر دو متن را به صورت دستی ترکیب می‌کنیم تا یک متن نهایی معنادار به دست آید.
   * تمامی مارکرها (`<<<<` و `====` و `>>>>`) را از فایل پاک می‌کنیم.
   * با دستور `git diff --check` مطمئن می‌شویم مارکری جا نمانده باشد.
   * با دستور `git add README.md` حل شدن مشکل را به گیت اعلام می‌کنیم.
   * با دستور `git commit` عملیات ادغام را نهایی می‌کنیم.
4. **لغو عملیات ادغام فعلی:** `git merge --abort`

### سؤال ۶: بازگرداندن تغییرات

1. **فقط دور ریختن تغییرات Staging نشده فایل:** `git restore notes.txt`. این دستور فایل را در Working Tree به وضعیتی که در Staging قرار دارد برمی‌گرداند.
2. **خارج کردن از Staging اما حفظ ویرایش در محیط کار:** `git restore --staged notes.txt`. فایل از محیط Staging خارج می‌شود اما کدهای شما در سیستم تغییر نمی‌کند.
3. **خنثی کردن کامیتِ پابلیش شده:** `git revert <commit-hash>`. این کار یک کامیت جدید می‌سازد که دقیقاً تغییرات کامیت اشتباه را معکوس می‌کند (مثل Control+Z، اما با ثبت در تاریخچه). حذف کامیت با `git reset` و Force Push کردن، تاریخچه مخزن راه دور را تغییر می‌دهد و تمام هم‌تیمی‌هایی که آن کامیت را قبلاً پول (Pull) کرده‌اند دچار مشکل جدی می‌شوند.
