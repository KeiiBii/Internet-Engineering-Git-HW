### سؤال ۱: merge و rebase

قسمت اول (عملکرد git merge): تغییرات یک شاخه را با شاخه جاری ترکیب می‌کند بدون اینکه تاریخچه کامیت‌های قبلی بازنویسی شود. معمولاً یک کامیت ادغام (Merge Commit) با دو والد ایجاد می‌کند که نشان‌دهنده ترکیب دو مسیر توسعه در تاریخچه است.
موقعیت استفاده این روش برای زمانی است که می‌خواهیم یک قابلیت تکمیل‌شده را در شاخه اصلی (مثلاً main) ادغام کنیم. دلیلش هم این است که شناسه کامیت‌ها را حفظ می‌کند و برای کار گروهی ایده‌آل است.

قسمت دوم (عملکرد git rebase): کامیت‌های شاخه جاری را برمی‌دارد و آن‌ها را روی آخرین وضعیت یک شاخه دیگر دوباره اعمال می‌کند. با این کار یک تاریخچه خطی و تمیز بدون کامیت ادغام ساخته می‌شود.
موقعیت استفاده این دستور برای به‌روزرسانی شاخه محلی خودتان با آخرین تغییرات main قبل از عملیات پوش (Push) است. دلیلش خواناتر شدن تاریخچه است، اما هرگز نباید روی شاخه‌هایی که قبلاً با هم‌تیمی‌ها به اشتراک گذاشته‌اید استفاده شود چون کار آن‌ها را مختل می‌کند.

### سؤال ۲: انتخاب بخشی از تغییرات

قسمت اول (مفهوم hunk): منظور از بخش یا hunk، مجموعه‌ای از تغییرات نزدیک به هم در یک فایل است که گیت در خروجی diff به همراه چند خط زمینه برای نشان دادن محل تغییر نمایش می‌دهد.

قسمت دوم (روش تعاملی): با استفاده از دستور git add -p وارد حالت تعاملی می‌شوید. گیت هر hunk را جداگانه نشان داده و از شما می‌پرسد چکار کند. برای اضافه کردن به ناحیه استیج از گزینه y، برای نادیده گرفتن از گزینه n و برای تقسیم به قطعات کوچک‌تر از گزینه s استفاده می‌شود.

قسمت سوم (فایده این کار): این روش کمک می‌کند تا تغییرات نامرتبط را از هم جدا کنید و کامیت‌های منطقی و تک‌هدفه بسازید تا بعداً بازبینی آن‌ها راحت‌تر باشد.

### سؤال ۳: یافتن منشأ خطا

قسمت اول (عملکرد git bisect): از جستجوی دودویی در تاریخچه برای یافتن اولین کامیتی که باعث ایجاد خطا شده است استفاده می‌کند.

قسمت دوم (مراحل جستجو): گام اول شروع با دستور git bisect start است. گام دوم تعیین نسخه خراب فعلی با git bisect bad و گام سوم تعیین یک نسخه سالم قدیمی با دستور git bisect good است.
پس از این مراحل، گیت یک کامیت میانی را می‌آورد تا شما تست کنید. اگر برنامه سالم بود دستور git bisect good و اگر خراب بود git bisect bad را می‌زنید. این کار اینقدر تکرار می‌شود تا کامیت معیوب پیدا شود. در نهایت برای خروج از دستور git bisect reset استفاده می‌شود.

قسمت سوم (مثال): فرض کنید بین ۶۴ کامیت یک باگ پیدا شده است. به جای تست تک‌تک آن‌ها، با این روش نهایتاً با ۶ بار تست به منشا باگ می‌رسید که بسیار در زمان صرفه‌جویی می‌کند.

### سؤال ۴: بررسی تغییرات پیش از کامیت

قسمت اول: دستور git diff تغییراتی که هنوز وارد استیج نشده‌اند را نشان می‌دهد. اما دستور git diff --cached تغییراتی که آماده کامیت هستند را نمایش می‌دهد.

قسمت دوم: اگر از دستور git commit استفاده کنید، فقط تغییراتی که در ناحیه استیج قرار دارند ثبت می‌شوند. تغییرات اضافه‌ای که فایل داشته اما هنوز Add نشده و همچنین فایل‌های پوشه tmp در محیط کار باقی می‌مانند. دلیلش این است که گیت فقط محتوای فعلی ناحیه استیج را برای کامیت کردن می‌خواند.

قسمت سوم: باید فایل gitignore. را در ریشه پروژه بسازید و نام پوشه /tmp/ را در آن بنویسید. اگر فایلی از قبل Track شده باشد، فقط اضافه کردنش به این فایل کافی نیست؛ اول باید با دستور git rm --cached آن را از حالت پیگیری خارج کنید.

### سؤال ۵: رفع merge conflict

قسمت اول: تداخل یا Conflict به این دلیل رخ می‌دهد که دو نفر دقیقاً یک خط مشابه از یک فایل را به دو شکل متفاوت تغییر داده‌اند. اگر تغییرات در فایل‌های متفاوت یا خطوط کاملاً مجزا باشد گیت معمولاً آن‌ها را به صورت خودکار ادغام می‌کند.

قسمت دوم: با دستور git status فایل‌های دارای اختلال مشخص می‌شوند. در این فایل‌ها علائم و مارکرهایی اضافه می‌شوند که مرز دقیق اختلافات را نشان می‌دهند.

قسمت سوم (مراحل رفع): برای رفع مشکل، فایل را در ادیتور باز می‌کنیم و دو متن را به صورت دستی ترکیب می‌کنیم تا متن نهایی معنادار شود. سپس تمامی مارکرها را پاک می‌کنیم و با دستور git diff --check مطمئن می‌شویم علامتی جا نمانده باشد. در آخر با دستور git add فایل را استیج کرده و با git commit عملیات ادغام را نهایی می‌کنیم.
برای لغو کردن عملیات ادغام هم می‌توان از دستور git merge --abort استفاده کرد.

### سؤال ۶: بازگرداندن تغییرات

قسمت اول: برای دور ریختن کامل تغییرات استیج نشده یک فایل از دستور git restore استفاده می‌شود که فایل را در سیستم به وضعیت آخرین کامیت برمی‌گرداند.

قسمت دوم: برای خارج کردن فایل از محیط استیج اما حفظ ویرایش‌های انجام شده روی سیستم، از دستور git restore --staged استفاده می‌کنیم.

قسمت سوم: برای خنثی کردن کامیتِ پابلیش شده باید از دستور git revert استفاده کرد. این کار یک کامیت جدید می‌سازد که تغییرات اشتباه قبلی را معکوس می‌کند. استفاده از git reset و Force push در این حالت کاملاً اشتباه است چون تاریخچه مخزن راه دور را تغییر می‌دهد و هم‌تیمی‌ها را دچار مشکل جدی می‌کند.
